## 1.目标与“什么算对”

在小组选定的重建执行机器上，确认选定版本的TripoSR能对2张不同的简单物体图片实际生成可读网格，确认Blender及对应打印检查工具能识别已知正常与问题网格，并得到可复现的环境、参数和打印配置记录。

“重建执行机器”可以是本机、队友电脑或小组已有GPU服务器。初版方案中的本机GPU只是一条历史检测信息，不能代表其他机器已经验证；迁移执行机器后重新记录环境并运行相同固定样例。

## 4.接口与边界

- P0验证现成工具的文件输入、命令行参数、返回码、日志与网格输出，不实现FastAPI、LangGraph、前端或业务适配器。
- P0开始前先记录现有环境和缺失项，确定固定输入、预期结果及基线命令；发生失败先入档，再进行必要的小范围环境调整和复验。
- 重建输出和几何检查结果分别记录，不能用“生成了文件”代替“网格检查通过”。
- Pydantic输入、输出、错误和证据模型的实现属于P1；对应设计草案见[接口与字段](../doc/接口与字段.md)，当前不创建这些业务类。
- 基础运行规则和模块边界见[架构设计](../doc/架构设计.md)，验收记录模板见[评估设计](../doc/评估设计.md)。
- 本任务不训练模型、不开发业务接口、不实现修复算法、不做多视图融合、不部署公网服务、不控制打印机。
- 当前轮次不执行本节技术步骤，也不为了完成文档而下载图片、软件、权重或准备业务测试代码。

## 5.错误行为与停止条件

| 场景 | 预期行为 |
| --- | --- |
| 执行机或样例尚未确定 | 标记待补材料，不填写推理成功率或耗时 |
| GPU、模型、Blender或检查工具缺失 | 明确记录缺失项，不编造结果，不静默换用其他后端 |
| 显存不足 | 记录原始错误；仅在已验证的低显存配置范围内重试1次，仍失败则停止并更新Bug/任务记录 |
| 工具超时或进程异常 | 停止当前试验，保留输入、参数、日志和退出码；不能填通过 |
| 自交或薄壁检查不能调用 | 标记未执行，P0不通过，先解决工具可行性再开展后续阶段 |
| 需要更换执行机器或技术路线 | 先更新当前任务、架构影响和验证计划，重新验证固定样例 |
| 完成文档约定但尚无技术证据 | 保持P0待启动，不进入P1 |

活动执行预算沿用技术方案：单次重建300秒、单次Blender操作120秒；预算变更先更新约定和原因，不在超时后静默放宽。
